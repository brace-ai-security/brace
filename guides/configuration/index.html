BRACE Guide · Configuration

The agent is a configuration

Reviewing the shipped code alone doesn't tell you what a running agent can do. An agent is a configuration of parts: a container, a harness (the loop that runs the model and hands it tools), a system prompt, a set of tools, memory, an identity, and a network path. Two agents built from the same model can behave very differently depending on those parts. Version and review the configuration along with the harness and tool code. Review generated code before it runs, too.

By Brenn Hill

The configuration decides what the agent can do. So the habits you already use for code have to apply to it too: version control, diff review, change approval, and drift detection (spotting when the running setup no longer matches the approved one). A one-line change to a system prompt can remove a guardrail with no pull request, no review, and no record. This guide covers the Configuration aspect: the harness and system prompt as reviewed artifacts, each release frozen and tied to the agent's identity, and drift detection for each agent.
The five principles
  1. Review configuration as well as code
  2. Version the system prompt and harness, and review changes
  3. Freeze each release and include its configuration in the agent’s identity
  4. Detect configuration drift for each agent
  5. Record the context behind each decision
PRINCIPLE 1

Review configuration as well as code

Review the running configuration alongside the application code. The container, harness, system prompt, tools, memory, identity, and network all shape what an agent can do.

Why it matters. The same model can behave very differently with different prompts, tools, and limits. A code review alone can miss those differences. Review configuration changes too, because they change both what the agent does and what it is allowed to do.

PRINCIPLE 2

Version the system prompt and harness, and review changes

Put the system prompt, rules files, and harness in version control. Change them only through review, the same way you change code. Allow production changes only through the approved release process, which records who made them.

Why it matters. The system prompt is policy. A prompt anyone can edit in production is unreviewed code with full control over the agent, and no record of who changed it. A one-line change can remove a guardrail or redirect the agent's goals. If a prompt or rules file can be edited live, there is no diff and no history to check. Review these changes the way you review code, so the rest of your controls can be trusted.

PRINCIPLE 3

Freeze each release and include its configuration in the agent’s identity

Freeze the full configuration for each release, so "what's running" is known and can be rebuilt. Then build its hash into the agent's identity, as the agent-type-id.

Operational scope. Write a release manifest that lists every part of the release. Keep a separate model record for the main model, sub-agent models, and helper models such as embedding models and rerankers. Record the provider, the exact model or checkpoint version, and any fine-tune or adapter version. Check each model ID against the provider's versioning docs. Mark it as a pinned snapshot or as an alias that can change. Even a pinned snapshot fixes only the weights, not the provider's serving systems. For training you run yourself, keep the training job ID, base model, dataset version, training code and config version, and output digest. For weights and adapters you host, include their digest and signature. Record the model name you asked for separately from the version the provider says it served. Label details the provider doesn't share. A release number or local hash can't prove that a provider's hidden state is unchanged.

Why it matters. Freezing turns the configuration from a moving target into a fixed reference you can rebuild. Building its hash into identity (see the Agent guide) means a later change shows up as a new ID when you recompute it, not as a silent edit. Check the running setup against the approved manifest, so a changed prompt, model, or tool can't keep the old approved identity. Together, these let you say exactly which configuration produced a behavior. You need that for both drift detection and tracing actions.

✗ Floating config
The prompt, tool list, and image tags can each change on their own between deploys. "What's running" is whatever someone touched last.
✓ Frozen & pinned
A release freezes the whole configuration. Its hash is the agent-type-id, so any change becomes a new, visible build.
PRINCIPLE 4

Detect configuration drift for each agent

Watch for drift in the things that define an agent build: container images, harness settings, prompts, MCP server lists, permissions, network policies, and model weights you host yourself. Check each agent, not just each host or cluster. When drift appears, raise an alert and block, quarantine, or roll back within a set time.

Why it matters. Configuration drifts. Someone patches a prompt in place, a tool list gains a server, or an egress rule loosens "just for debugging." Infrastructure-as-code drift detection compares the running state with a declared baseline. Teams usually run it per host, and agent-level changes hide below that level. Running the same comparison for each agent build brings them to light.

PRINCIPLE 5

Record the context behind each decision

A record of the configuration that ran is incomplete without two more things: how full the model's context was at each decision, and the prompt a parent gave each sub-agent.

Why it matters. What produced a behavior is more than the static files. How full the context was at a decision, and what a parent told a sub-agent at run time, both shape what happened. Neither is in the frozen artifacts. Record them (see the Run-time and Agent guides) and link them to the release manifest from each trace. Then "what ran" covers the inputs that change at run time as well as the pinned ones.

✗ Static only
You can rebuild the files but not the run. There is no record of context size at each decision, or of the prompt a parent passed down.
✓ Full picture
Context size at each decision and the prompts parents passed down are logged and linked to the pinned configuration.

Worked example — a coding agent whose behavior is its config

An internal coding agent uses a fixed model. Its behavior depends on its harness, prompt, rules files, and tools. Here is how the principles apply.

  • Config as the artifact (P1): the security review covers the harness, system prompt, rules files, MCP configuration, and tool list alongside the application code.
  • Reviewed artifacts (P2): the system prompt and rules files live in version control and change only through reviewed pull requests.
  • Frozen & pinned (P3): each release freezes the whole configuration, and its hash is the agent-type-id. The model is recorded as a pinned snapshot, not an alias that can change.
  • Drift detection (P4): a check compares the running prompt, MCP list, and egress policy with the pinned baseline. It alerts on any difference.
  • Observables (P5): context size at each decision and the prompts parents passed down are logged, so you can rebuild the run, not just the files.

A prompt edited directly in production shows up as drift against the pinned baseline within the set detection time. It doesn't quietly change how every developer's agent behaves.
