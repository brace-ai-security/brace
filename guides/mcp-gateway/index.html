BRACE Guide · Ecosystem deep dive

Build an MCP gateway that agents cannot bypass

A gateway can authenticate, authorize, scan, meter, and log MCP calls. It works as a control when it is the only usable path to the tools it governs. Choose network and credential controls for internal or public HTTP services, and host or sandbox controls for local stdio tools. Test every alternate route, including CLI/code mode.

By Brenn Hill

A gateway is the network-firewall pattern applied to MCP traffic: one choke point, which you can audit, that every tool call passes through. The Ecosystem guide covers what to enforce there. This deep dive covers what makes it real. The selected boundary must be the only usable path to governed tools, enforced through network, credential, and local-process controls appropriate to the deployment. It must also meter access.

Scope, standards, and credentials

This guide covers internal HTTP servers, public third-party MCP services, and local stdio tools. Choose the enforcement mechanism for each deployment. A private network and mutual TLS are one strong internal pattern; you cannot require a third-party service to use your private network. Local processes need controls in the host or sandbox.

Two authorization boundaries. The agent authenticates to the gateway with a credential valid for that gateway. The gateway separately obtains an access token for the backend from an issuer that backend trusts, using a supported grant or token exchange. Check issuer, audience, expiry, and grants at each boundary. Never accept a token intended for another resource or forward it unchanged as a substitute for backend authorization. A gateway cannot mint credentials that an arbitrary API will accept.

Identity and authority are separate. Identify the acting agent and the user or system whose authority it uses. Short-lived access tokens can represent either machine authority or explicitly delegated user authority. A service account is one possible agent identity, not the definition of an access token. Static API keys and personal access tokens are different credentials. Where a backend only supports static keys, isolate them at the gateway, limit their permissions, and record the lifetime and revocation gap. A vault stores backing secrets; a trusted issuer supplies expiring access grants.

Protocol baseline, checked 2026-10-16. Use the MCP 2026-07-28 authorization specification, Streamable HTTP transport, and official security guidance. MCP authorization is optional at the protocol level; BRACE requires authentication and action authorization for protected tool access. An OAuth deployment follows the applicable discovery, resource-indicator, PKCE, issuer-response, and audience-validation requirements. Prefer Client ID Metadata Documents; Dynamic Client Registration is deprecated. Protect discovery and redirect fetches against SSRF.

Additional mechanisms. RFC 9700 is OAuth security best current practice; RFC 8693 defines token exchange where supported. Enterprise-Managed Authorization is a stable optional MCP extension; MCP Client Credentials remains draft at this review. Check client, server, and issuer support. Project-specific gateway specifications and industry deployment reports are design references, not universal MCP conformance standards.

THE RULE

It must be the only door

Make the gateway or equivalent enforcement layer the only usable path from this agent to its governed tools. Control both network access and credentials. Apply that boundary to HTTP calls, dynamic tools, CLI/code mode, and wrappers; an alternative execution path must not skip policy.

Why it matters. A gateway you can bypass is not a control. It is a suggestion. Scanning, allow and deny rules, rate limits, and audit only hold if there is no other way to call the tool. The threat is an agent that no longer cooperates, because it was hijacked by prompt injection or is misaligned. So you can't rely on the agent choosing to use the gateway. Make the direct call impossible, not just discouraged. The network and the credentials do that, not the agent's code.

Choose controls for each deployment

Every pattern must prevent the agent from skipping authorization. Use the controls that apply to its actual routes and execution environment.

  1. Internal HTTP servers. Restrict agent egress to approved enforcement endpoints. Place backends on private networks where possible and authenticate the gateway to them, for example with mTLS. Keep backend access tokens and secrets out of agent-controlled processes. Other essential routes, such as model access, need their own approved boundary.
  2. Public third-party services. Enforce agent-side egress and credential restrictions so direct calls cannot exercise the protected authority. Keep third-party tokens and refresh credentials in the broker. Use the provider's supported OAuth flow or token exchange and preserve tenant/resource limits. Public availability alone does not mean the agent can authenticate. Test alternate hosts, redirects, proxy settings, and shell/SDK routes; disable a path whose bypass you cannot prevent.
  3. Local stdio servers. Control who can launch the process and which pinned binary or image runs. Give it only approved files, environment variables, secrets, and network access. Local transport is not a sandbox. An HTTP gateway does not protect a separate local process that can read host credentials or invoke tools directly.
✗ Gateway as a courtesy
The SDK is set to use the gateway, but agents run with normal network access and hold the tools' API keys. A prompt-injected agent simply calls the server directly with those keys.
✓ Gateway as the only door
Agents run in a sandbox that can reach only the gateway. Internal servers authenticate the gateway, for example over mTLS. Backend credentials live in the gateway. The direct call has no route and no tool credential.
THE SOURCE OF TRUTH

A gateway is only as good as its registry

An allowlist needs a list. Behind the gateway sits an MCP inventory: a registry of which servers and tools exist, who approved each, its vetted fingerprint, its trust tier, and which agent roles may use it. The gateway enforces. The registry is what it enforces.

Why it matters. To approve a tool, check its fingerprint, or limit it by role, you first have to record it in the inventory. "Shadow MCP" risk is a server someone wired up that no inventory knows about, so no control covers it. The registry closes that gap. It also holds the rug-pull baseline: the fingerprint the gateway re-checks on load is the one the registry recorded at approval. And it holds the role-to-tool map, so the gateway can filter the list of tools each agent sees, not just individual calls.

A workable registry entry holds, for each tool: a stable identity made of a verified server identity plus the tool name, the vetted fingerprint (a hash of its description and schema), an owner and approval date, a trust tier, the agent roles allowed to call it, and a pointer to its credential in the vault. Base server identity on the verified endpoint, credential, or registry namespace, never on the name the server reports about itself (serverInfo). Each call uses an approved registry/policy version. Bound and test how long config changes take to reach every executor; stale grants must not survive the revocation limit. Nothing reaches an agent until the registry has admitted it.

Publication is a controlled lifecycle

Discover tools into a disabled state. The service owner reviews the publisher, description, schemas, permissions, and implementation reference, then approves and enables a version. Re-check on load, cache refresh, and tool-list change. Quarantine unexpected changes until reviewed. Keep approval history, propagation times, and a tested rollback; rollback must not restore revoked permissions. Fingerprints cover metadata, not hidden remote implementation changes.

✗ No inventory
Servers are wired up as needed. "Allow" means whatever each agent's config happens to list. A server nobody recorded answers calls that no control covers.
✓ Registry-backed
Every server and tool is registered with a fingerprint, owner, trust tier, and allowed roles. The gateway admits only what is in the registry, filtered to the calling agent's role.

What the gateway enforces, in order

Once every call has to pass through it, the gateway is where you apply the ecosystem controls the same way for every agent, instead of building them again for each one. A single tool call goes through these steps. Order matters: cheap rejections first, the costly forward last, and any failure ends in a denial.

  1. Authenticate the caller. Prove which agent is calling, by its own identity, such as a dedicated service account or workload identity, rather than an account shared across agents. For HTTP and OAuth, check the access token's issuer, intended audience, expiry, and scopes. Deny a call that fails authentication. Validate the gateway-facing credential for this resource and obtain separately authorized credentials for each backend. Preserve the original subject and current agent identity. (This is the agent identity from the Agent aspect. The gateway is where it's checked.)
  2. Authorize against the agent's role and identity. First, reject any request whose Mcp-* headers don't match its body, so policy can't approve one tool while the body calls another. Then check a least-privilege allowlist tied to the verified agent, delegated subject, tenant, and task: may it call this tool with these kinds of arguments? Deny by default. The list of available tools is also filtered by role, so an agent can't even see, let alone call, tools outside its job. Use the approved registry/policy version. Enforce the same decision in dynamic tools, CLI/code mode, and wrappers. An identity chain records provenance; it does not itself approve an action. For RFC 8693 tokens, prior nested actors grant no additional access. Don't base allow or approval decisions on a tool's own annotations, such as “read-only.” MCP treats them as untrusted unless you trust the server.
  3. Validate the call and inspect the tool. Compare the hash of the tool's description and schema with the approved fingerprint. That catches the metadata changes of a rug pull. It can't reveal hidden changes to remote code. If the re-check fails, don't serve the cached definition. Scan all metadata for hidden instructions: server instructions, names, descriptions, schemas, annotations, and templates. Validate argument schemas. Check for obvious attempts to send data out, such as a url pointing outside the allowlist.
  4. Reserve budget before forwarding. Before sending the call, check and reserve its call and cost allowance in one step, counting parallel calls and sub-agents. Record the approved attempt before any side effect. Set a fixed tolerance for costs known only after the call runs.
  5. Forward with a short-lived access token added by the gateway. Only now does the call leave the gateway over a protected connection, using mTLS where the deployment supports it. It carries a short-lived token issued for this backend, bounded by the agent's approved task and any delegated user/system authority. The agent-controlled runtime never receives the backend credential. A gateway-facing token cannot be reused at the backend. Enforce expiry and the measured revocation limit.
  6. Validate and scan the response. Treat the tool's output as untrusted input on the way back. Remove anything that looks like a secret before it reaches the model's context or your logs. Reject or hold aside suspicious content, according to policy. Scans can miss an injection hidden in a well-formed response. So keep data separate from instructions, and enforce action permissions separately. Data hygiene runs both ways.
  7. Reconcile usage and record the outcome. Compare actual usage with the reserved budget. Add the outcome, agent identity, tool, argument hash, decision, and latency to the append-only audit trail.
  8. Fail closed. If any step errors, deny. Examples: the scanner is down, the fingerprint store can't be reached, or the policy engine times out. A check that can't run is a denial, never a silent pass. A scanner that quietly lets unchecked content through creates false confidence. Block high-impact actions when required audit capture isn't working.

Request state, caches, and extensions

MCP 2026-07-28 removes protocol-level sessions: requests carry their own metadata. A connection, process, conversation label, or self-reported client/server name is not an authenticated principal. For older versions, test their session-binding rules separately. Authorize every use of an explicit task ID, state handle, or resource URI; knowing its value is not authorization.

Key private tool-list/result caches by verified authorization context, tenant, resource, and policy version, with expiry or invalidation that meets the revocation limit. Share only results explicitly approved as public under the server's cache policy. Test a second tenant, a lower-privilege caller, and a revoked grant against both cached data and task handles.

Inventory protocol and extension versions. For Tasks, test access to status/results, cancellation, ownership, and shutdown with work in flight. For MCP Apps, test the host's iframe sandbox, declared CSP, bridge-message validation, and authorization of UI-initiated tool calls. A gateway cannot enforce browser-host boundaries it never sees. Assign the remaining controls to the host. Deprecated sampling, roots, logging, and legacy HTTP+SSE paths still need review while enabled; deprecation does not disable them.

Meter and control access through the choke point

Every call passes through one place, so that is also where you meter tool access. Metering is a security control, not just an accounting one. The gateway already knows which agent called which tool, with what arguments, and how often. Use it.

Why metering belongs in the gateway. The first visible sign of a misaligned or hijacked agent is often volume. It calls an API in a tight loop until the bill spikes, or reads a data source in bulk when it should read a little. Quotas for each agent and tool turn an open-ended incident into a capped one. And because the gateway sits in the path of every call, the meter is also a throttle and a stop point. It can slow, cap, or cut off one agent or one tool without redeploying anything.

  • Per-agent, per-tool quotas and rate limits. A cap on calls and on cost per time window, for each agent and tool. Going over it slows or denies calls, and raises an alert.
  • Cost attribution. Every call is priced and tied to an agent, a tenant, and an owner. So you can answer "which agent spent this?" the same way you answer "which agent did this?"
  • Anomaly signals. Keep a baseline for each agent and tool. Flag a sudden change in call rate, unusually random arguments, or unusual tool combinations as a security event, separate from quality monitoring.
  • A central cut-off. The gateway can deny new calls by an agent, or quarantine a tool for all agents, within a measured time limit. Calls already running, and actions already done, need separate handling. This is the ecosystem half of the kill switch.

A minimal build

For an HTTP gateway, this reference design has seven parts. A local stdio integration needs equivalent controls in its host or sandbox:

  1. A proxy front end that speaks MCP to agents and to servers. It is the one endpoint every agent is set up, and network-restricted, to use.
  2. A registry or inventory, the source of truth above: approved servers and tools, each with a fingerprint, owner, trust tier, allowed roles, and a credential pointer.
  3. A policy engine that checks the registry's allowlist, role filter, and quotas on every call, and denies by default.
  4. Scanners for the tool fingerprint, tool metadata, request arguments, and response body. Each can block, clean, or log.
  5. A credential broker that obtains short-lived access tokens from a trusted issuer or through supported token exchange and adds the right scoped token to each call. A secrets vault holds any required backing secrets, including static API keys for services that require them; agents never receive those secrets or tool access tokens.
  6. A meter that records calls and cost for each agent and tool, enforces quotas, and sends anomaly signals.
  7. An append-only audit store that records every decision, so you can trace who did what and investigate later.

Wrap all seven so that any internal failure returns a denial to the agent. Then enforce the boundary for each deployment: approved agent egress, separately authorized backends, broker-held backend credentials, and restricted local processes. Now you have a real gateway, not a hint.

Reference specification. Separate protocol conformance from architecture guidance. Microsoft's Agent Governance Toolkit includes a project-specific MCP Security Gateway specification. It sets conformance requirements for interception, scanning, schema-drift detection, and fail-closed behavior. It doesn't prove that any product conforms. BRACE defines what to enforce at the MCP boundary and why it must be the only door. That spec is one concrete way to build the box.

Three ways a gateway quietly fails

Each of these looks like a gateway in an architecture diagram, but isn't one in practice.

✗ The bypassable gateway
Agents can invoke tools outside policy through direct routes, alternative execution paths, or leaked backend credentials. Those calls bypass the gateway controls.
✗ The fail-open gateway
When a scanner or the policy store errors, the call goes through "so the agent isn't blocked." Now an attacker just has to make the check fail.
✗ The log-only gateway
It sees every call but can't deny one. You get a perfect record of the breach you couldn't stop. Logging is necessary, but it is not enforcement.
✓ The real gateway
Every governed tool call passes the selected enforcement boundary. It denies by default, fails closed, enforces budgets, and can stop further calls. These controls must work even when the agent does not cooperate.

Evidence, deployment examples, and further reading

Uber's deployment reports. Solving the Identity Crisis for AI Agents (May 2026) describes registry-verified agent identities, SPIRE-backed workloads, and short-lived per-hop tokens with delegation context. Its exchange is customized; preserved history is not proof of action approval. Designing MCP Gateway (October 2026) describes separate registry/control and proxy/data planes, disabled-by-default tools, owner-reviewed changes, and CLI calls through the gateway. These are reported practices, not independent security certification or a universal MCP architecture.

Deployment guidance. Use OWASP's secure server development guide and third-party server guide alongside the protocol. agentgateway's token-exchange documentation is one implementation reference, not a requirement to use that product.

Attack and scanner evidence. MCPTox tests poisoned tool metadata. MCP-SafetyBench and MCP Security Bench exercise broader tool workflows. The MCPZoo/scanner study finds substantial disagreement, false alarms, and missed vulnerabilities in its sample. A clean scan is one piece of evidence. Keep allowed-task results, concrete negative tests, scanner versions, false positives, and misses; do not turn benchmark attack rates into a production risk estimate.

Gateway go / no-go

One way to build the MCP boundary, extending Principle 5 of the Ecosystem guide. The full checklist sets the release gates and acceptable tradeoffs. Choose internal, third-party, or local controls for each integration. The private-network/mTLS diagram is one example. See E02–E06 and E10–E11 and their verification recipes. A clean content scan can't prove that every prompt injection was caught, so limit each agent's authority separately.

  • Agents are network-restricted so the gateway is their only route to any tool server.
  • Internal, public third-party, and local stdio paths each have tested network, credential, and host controls appropriate to their deployment.
  • New tools start disabled. Owners approve versioned definitions and grants; re-checks, quarantine, config propagation, and rollback are tested.
  • The gateway obtains and attaches short-lived, scoped access tokens for tool calls; agents never receive them. If a service only supports static API keys, keep them in the gateway and record the lifetime and revocation gap.
  • Every call is authenticated to a specific agent identity and authorized against a registry-backed allowlist for the agent's role (deny by default). The list of available tools is filtered by the agent's role.
  • Header/body mismatches are rejected before routing or policy relies on them. Private caches and explicit task/state handles are isolated by verified authorization context and tenant, including after policy changes.
  • Gateway/backend audiences, delegated subjects, dynamic tools, CLI/code mode, task cancellation, and enabled Apps boundaries have positive and negative tests.
  • Calls and responses are scanned, the tool fingerprint is re-checked, and any check failure denies (fail closed).
  • Per-agent, per-tool quotas and cost metering are enforced, with anomaly alerts and a central cut-off.
  • Every decision is written to an append-only audit trail.
