Build an MCP gateway that agents cannot bypass

A gateway in front of your MCP servers is the one place you can authenticate, authorize, scan, meter, and log every tool call. But a gateway only works if it is the only path to your tools. If an agent can reach an MCP server directly, the gateway is optional, and a hijacked or misaligned agent will go around it. This guide shows how to build the gateway, and how to make it impossible to bypass.

By Brenn Hill

A gateway is the network-firewall pattern applied to MCP traffic: one choke point, which you can audit, that every tool call passes through. The Ecosystem guide covers what to enforce there. This deep dive covers what makes it real. The gateway must be the only route from an agent to a tool, enforced by the network. And it must meter what passes through, so you can control and account for access.

Scope and practical limits. This guide describes a gateway for remote HTTP tools. Local MCP servers that talk over standard input/output (stdio) need the same controls in the host or sandbox. An HTTP gateway doesn't control their processes, files, credentials, or network. Tokens for the services behind the gateway must come from an authority those services trust, with the right audience and scope. A gateway can't invent a token that any API will accept. Where only fixed keys exist, keep them behind the gateway, limit what they can do, and write down the gap in lifetime and revocation. MCP 2026-07-28 is the current version. Under it, the gateway must reject any request whose copied Mcp-* headers don't match the body, before it checks policy. Store any cached tool list or response separately for each authorization context. Where the gateway is itself an OAuth client, check the authorization server's issuer (iss, RFC 9207). Prefer Client ID Metadata Documents for client registration. Dynamic Client Registration is deprecated. Also protect discovery URLs against SSRF (tricking a server into calling places it shouldn't). See MCP authorization, 2026-07-28, the Streamable HTTP transport, and checklist E06.

THE RULE

It must be the only door

Set up your MCP servers so they can be reached only through the gateway. If an agent has any other route to a tool, such as a direct network path or its own credentials, every gateway control is optional. The agent that most needs stopping is the one that will go around it.

Why it matters. A gateway you can bypass is not a control. It is a suggestion. Scanning, allow and deny rules, rate limits, and audit only hold if there is no other way to call the tool. The threat is an agent that no longer cooperates, because it was hijacked by prompt injection or is misaligned. So you can't rely on the agent choosing to use the gateway. Make the direct call impossible, not just discouraged. The network and the credentials do that, not the agent's code.

How to make it non-bypassable

Three things must all be true. None is optional.

  1. Network isolation on the agent side. The agent's runtime can connect to the gateway and nothing else. Its egress policy blocks every other route: no direct path to tool servers, and no open internet. (This is the same per-agent egress allowlist from Build-time, aimed at your tools.)
  2. Private, gateway-only servers. MCP servers sit on a private network segment with no public route. They accept connections only from the gateway, enforced with mutual TLS, not just an IP allowlist. A server that answers anyone is a back door.
  3. The agent holds no tool credentials, and the ones the gateway adds are short-lived. The gateway gets a short-lived token, limited to what that agent is allowed to do, from the destination's trusted issuer or through a supported token exchange. An agent with no key can't authenticate to a server even if it finds a route. Set and test the token's lifetime and grants. Don't assume every issuer supports tokens limited to a single call. Where only fixed credentials exist, apply the limits and record the gap described above.
✗ Gateway as a courtesy
The SDK is set to use the gateway, but agents run with normal network access and hold the tools' API keys. A prompt-injected agent simply calls the server directly.
✓ Gateway as the only door
Agents run in a sandbox that can reach only the gateway. Servers accept only the gateway, over mTLS. Credentials live in the gateway. The direct call has no route and no key.
THE SOURCE OF TRUTH

A gateway is only as good as its registry

An allowlist needs a list. Behind the gateway sits an MCP inventory: a registry of which servers and tools exist, who approved each, its vetted fingerprint, its trust tier, and which agent roles may use it. The gateway enforces. The registry is what it enforces.

Why it matters. To approve a tool, check its fingerprint, or limit it by role, you first have to record it in the inventory. "Shadow MCP" risk is a server someone wired up that no inventory knows about, so no control covers it. The registry closes that gap. It also holds the rug-pull baseline: the fingerprint the gateway re-checks on load is the one the registry recorded at approval. And it holds the role-to-tool map, so the gateway can filter the list of tools each agent sees, not just individual calls.

A workable registry entry holds, for each tool: a stable identity made of a verified server identity plus the tool name, the vetted fingerprint (a hash of its description and schema), an owner and approval date, a trust tier, the agent roles allowed to call it, and a pointer to its credential in the vault. Base server identity on the verified endpoint, credential, or registry namespace, never on the name the server reports about itself (serverInfo). The gateway reads the registry on every call. Nothing reaches an agent unless the registry has admitted it.

✗ No inventory
Servers are wired up as needed. "Allow" means whatever each agent's config happens to list. A server nobody recorded answers calls that no control covers.
✓ Registry-backed
Every server and tool is registered with a fingerprint, owner, trust tier, and allowed roles. The gateway admits only what is in the registry, filtered to the calling agent's role.

What the gateway enforces, in order

Once every call has to pass through it, the gateway is where you apply the ecosystem controls the same way for every agent, instead of building them again for each one. A single tool call goes through these steps. Order matters: cheap rejections first, the costly forward last, and any failure ends in a denial.

  1. Authenticate the caller. Prove which agent is calling, by its own identity, not a shared service account. For HTTP and OAuth, check the token's issuer, intended audience, expiry, and scopes. Deny a call that fails authentication. Never pass an unchecked token through to the services behind the gateway. (This is the agent identity from the Agent aspect. The gateway is where it's checked.)
  2. Authorize against the agent's role and identity. First, reject any request whose Mcp-* headers don't match its body, so policy can't approve one tool while the body calls another. Then check a least-privilege allowlist tied to this agent's identity and role: may it call this tool with these kinds of arguments? Deny by default. The list of available tools is also filtered by role, so an agent can't even see, let alone call, tools outside its job. Read the allowlist and the role-to-tool map from the registry, not from code for each agent. Don't base allow or approval decisions on a tool's own annotations, such as “read-only.” MCP treats them as untrusted unless you trust the server.
  3. Validate the call and inspect the tool. Compare the hash of the tool's description and schema with the approved fingerprint. That catches the metadata changes of a rug pull. It can't reveal hidden changes to remote code. If the re-check fails, don't serve the cached definition. Scan all metadata for hidden instructions: server instructions, names, descriptions, schemas, annotations, and templates. Validate argument schemas. Check for obvious attempts to send data out, such as a url pointing outside the allowlist.
  4. Reserve budget before forwarding. Before sending the call, check and reserve its call and cost allowance in one step, counting parallel calls and sub-agents. Record the approved attempt before any side effect. Set a fixed tolerance for costs known only after the call runs.
  5. Forward with a short-lived credential added by the gateway. Only now does the call leave the gateway, over mTLS. It carries a short-lived, narrowly scoped token from an issuer the tool trusts. The agent never receives this credential. Enforce the token's set expiry.
  6. Validate and scan the response. Treat the tool's output as untrusted input on the way back. Remove anything that looks like a secret before it reaches the model's context or your logs. Reject or hold aside suspicious content, according to policy. Scans can miss an injection hidden in a well-formed response. So keep data separate from instructions, and enforce action permissions separately. Data hygiene runs both ways.
  7. Reconcile usage and record the outcome. Compare actual usage with the reserved budget. Add the outcome, agent identity, tool, argument hash, decision, and latency to the append-only audit trail.
  8. Fail closed. If any step errors, deny. Examples: the scanner is down, the fingerprint store can't be reached, or the policy engine times out. A check that can't run is a denial, never a silent pass. A scanner that quietly lets unchecked content through creates false confidence. Block high-impact actions when required audit capture isn't working.

Meter and control access through the choke point

Every call passes through one place, so that is also where you meter tool access. Metering is a security control, not just an accounting one. The gateway already knows which agent called which tool, with what arguments, and how often. Use it.

Why metering belongs in the gateway. The first visible sign of a misaligned or hijacked agent is often volume. It calls an API in a tight loop until the bill spikes, or reads a data source in bulk when it should read a little. Quotas for each agent and tool turn an open-ended incident into a capped one. And because the gateway sits in the path of every call, the meter is also a throttle and a stop point. It can slow, cap, or cut off one agent or one tool without redeploying anything.

  • Per-agent, per-tool quotas and rate limits. A cap on calls and on cost per time window, for each agent and tool. Going over it slows or denies calls, and raises an alert.
  • Cost attribution. Every call is priced and tied to an agent, a tenant, and an owner. So you can answer "which agent spent this?" the same way you answer "which agent did this?"
  • Anomaly signals. Keep a baseline for each agent and tool. Flag a sudden change in call rate, unusually random arguments, or unusual tool combinations as a security event, separate from quality monitoring.
  • A central cut-off. The gateway can deny new calls by an agent, or quarantine a tool for all agents, within a measured time limit. Calls already running, and actions already done, need separate handling. This is the ecosystem half of the kill switch.

A minimal build

You don't need a platform to start. This design has seven parts, starting with an MCP reverse proxy:

  1. A proxy front end that speaks MCP to agents and to servers. It is the one endpoint every agent is set up, and network-restricted, to use.
  2. A registry or inventory, the source of truth above: approved servers and tools, each with a fingerprint, owner, trust tier, allowed roles, and a credential pointer.
  3. A policy engine that checks the registry's allowlist, role filter, and quotas on every call, and denies by default.
  4. Scanners for the tool fingerprint, tool metadata, request arguments, and response body. Each can block, clean, or log.
  5. A credential broker (a secrets vault) that holds tool credentials and adds the right scoped one to each call, so agents never hold keys.
  6. A meter that records calls and cost for each agent and tool, enforces quotas, and sends anomaly signals.
  7. An append-only audit store that records every decision, so you can trace who did what and investigate later.

Wrap all seven so that any internal failure returns a denial to the agent. Then enforce the three no-bypass properties around it: isolated agents, private gateway-only servers, and no credentials held by agents. Now you have a real gateway, not a hint.

Reference specification. You don't have to invent the spec. Microsoft's open MCP Security Gateway 1.0 (part of the MIT-licensed Agent Governance Toolkit) is a draft specification. It sets conformance requirements for interception, scanning, schema-drift detection, and fail-closed behavior. It doesn't prove that any product conforms. BRACE defines what to enforce at the MCP boundary and why it must be the only door. That spec is one concrete way to build the box.

Three ways a gateway quietly fails

Each of these looks like a gateway in an architecture diagram, but isn't one in practice.

✗ The bypassable gateway
Agents can still reach servers directly or hold the credentials. Calls that bypass the gateway also bypass its controls.
✗ The fail-open gateway
When a scanner or the policy store errors, the call goes through "so the agent isn't blocked." Now an attacker just has to make the check fail.
✗ The log-only gateway
It sees every call but can't deny one. You get a perfect record of the breach you couldn't stop. Logging is necessary, but it is not enforcement.
✓ The real gateway
The gateway mediates every tool call, denies access by default, fails closed, enforces budgets, and can stop further calls. These controls must work even when the agent does not cooperate.

Gateway go / no-go

One way to build the MCP boundary, extending Principle 5 of the Ecosystem guide. The full checklist sets the release gates and acceptable tradeoffs. The mTLS and credential-broker design in this guide is one way to meet them. See E02–E06 and E10–E11 and their verification recipes. A clean content scan can't prove that every prompt injection was caught, so limit each agent's authority separately.

  • Agents are network-restricted so the gateway is their only route to any tool server.
  • MCP servers are on a private segment and accept connections only from the gateway, over mutual TLS.
  • Every MCP server and tool is in an inventory/registry — fingerprint, owner, trust tier, permitted roles — and the gateway admits only what is registered.
  • Tool credentials live in the gateway and are injected as short-lived, scoped tokens per call; agents hold none.
  • Every call is authenticated to a specific agent identity and authorized against a registry-backed allowlist for the agent's role (deny by default). The list of available tools is filtered by the agent's role.
  • Requests whose Mcp-* headers don't match the body are rejected before policy runs. Cached tool lists are kept separate for each authorization context.
  • Calls and responses are scanned, the tool fingerprint is re-checked, and any check failure denies (fail closed).
  • Per-agent, per-tool quotas and cost metering are enforced, with anomaly alerts and a central cut-off.
  • Every decision is written to an append-only audit trail.
