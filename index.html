BRACE Framework

A practical security framework for teams that build and operate autonomous AI agents, the kind that plan, call tools, change real systems, and spawn sub-agents without a human reviewing each action.

The idea

Why agent security needs its own framework.

An autonomous agent combines code with a runtime configuration: a container, a harness (the loop that runs the model and hands it tools), a system prompt, a set of tools, a memory store, an identity, and a network path. Two agents built from the same model can behave completely differently depending on how those parts are configured. Review the configuration together with the harness, tools, and generated code. Code review is still needed, but it does not show you the whole running agent.

Nine controls, three observability requirements

Every control and observability requirement depends on two things: agent settings and shared infrastructure and services. Review both.

Build-time, fixed when the agent is built

C1

Architecture

Isolate the environment and network. Allow only the destinations the task needs.

C2

Capability-scoped API access

Narrowly scoped, short-lived access tokens, rather than static API keys. Identify the agent separately from the user or system it acts for. Revoke the agent's access without cutting off the user.

C3

Container

Pinned, signed, and minimal, with a stronger sandbox for untrusted code. The image hash is part of the agent's identity.

C4

Harness

Allowed tools, limits, and destructive actions blocked unless that exact action is approved.

Run-time, active on every execution

C5

Data

Treat all outside input as untrusted. Assume some injections will work.

C6

Memory

Separate memory, check writes, and record where each entry came from.

C7

Behavioral

Security monitoring, kept separate from answer-quality monitoring.

Closure, stop and explain

C8

Kill switch

A tested stop for the agent and its sub-agents that the agent can't disable.

C9

Audit trail

A full record of every action, not just the output. The agent can't erase it.

Observability, the data the controls depend on

Obs-T1

Required identity fields

Six fields per action, including a content-hashed agent-type-id.

Obs-T2

Context-size logging

How full the context was at each decision. Unknown is never zero.

Obs-T3

Sub-agent provenance

Which sub-agent ran, and the prompt the parent gave it.

Ship them in this order

Build the twelve elements in stages, applying the checklist’s release gates at each stage.

Tier 1, Prevent damage, preserve attribution

Destructive-action interception, capability-scoped access tokens, a tested kill switch, an audit trail, and the six identity fields.

Tier 2, Harden the substrate, surface invisible failures

Environment and egress isolation, a signed minimal container, input validation, context-size logging.

Tier 3, Active detection

Behavioral monitoring with sequence-pattern baselines, memory provenance, sub-agent and parent-prompt provenance.

If you adopt only part of BRACE, you still carry the rest of the risk. You are accepting it on purpose, not removing it.

How BRACE fits with other frameworks

Use OWASP and MITRE to know what can go wrong. Use BRACE to know what to build, and in what order.

  • OWASP Top 10 for Agentic Applications, a threat catalog. It names ten risks (ASI01–ASI10). BRACE names the controls that reduce them.
  • MITRE ATLAS, a catalog of attacker techniques against AI systems. See the ATLAS mapping.
  • OWASP Top 10 for Agentic Applications / OWASP MCP Top 10, lists of the main security risks for agents and MCP. See the Agentic Top 10 mapping and the MCP Top 10 mapping.
  • NIST AI RMF / ISO/IEC 42001, references for governance and management systems. BRACE adds technical checks for each deployment alongside them. See the AI RMF mapping and the ISO/IEC 42001 mapping.
  • LoopRails, human oversight. BRACE secures the agent itself. Getting the human review step right is a design problem as much as a security one, so LoopRails covers it: how much review each action needs, and how to design review that catches mistakes instead of becoming a rubber stamp. Use the two together.
  • Eval-Driven Development, correctness and quality. BRACE secures the agent. Eval-driven development checks that what the agent produces is good enough to keep. Security, oversight, and quality work together.

High-risk use. BRACE reports what it checked, what it found and what remains unknown; it does not issue a GO/NO-GO deployment verdict for high-stakes or high-autonomy use. Accountable people own any gradual, closely monitored rollout, with bounded exposure, stop conditions, tested recovery and review before expansion.

Status. BRACE brings together agent-security practices already used in production. It is not yet a validated standard. The individual controls are widely used. BRACE adds one way to organize them and logging for each agent. It is an open project that keeps changing. Apply it, critique it, and contribute.
