# Invoice agent threat model — revised smoke exercise

Basis: [invoice-design.md](../invoice-design.md), unversioned “Proposed invoice agent”; assessment date 2026-10-23. This models stated requirements. There is no observed implementation, runtime evidence, qualification, confirmed vulnerability or deployment decision. All responses below are **proposed**; existing design statements are **claimed** only.

## Scope, actors and assets

The intended outcome is invoice processing using inbound vendor email/invoices, tenant ERP invoice and bank reads, `pay_invoice` and `send_email`. Human approval is planned. Permitted amounts, recipients, bank changes, tenant roles, autonomous actions and forbidden business operations are unspecified. Worst credible harm is financial loss plus cross-tenant bank/invoice disclosure and persistent unauthorized work. The model excludes live services, exploitation and incident handling.

| Assets | Actors and known ownership | Coverage |
|---|---|---|
| Money, invoice/payment state, beneficiary details | Tenant finance users/approvers unspecified; ERP owner unknown | INV-01, INV-02, INV-05 |
| Tenant ERP/bank records, email and attachments | Vendors control incoming content; ERP/email/provider data owners unknown | INV-01, INV-02, INV-03 |
| Parent/helper credentials and delegated authority | Classifier shares parent credentials; identity owner unknown | INV-02, INV-06 |
| Extracted vendor memory, summaries and derived copies | Shared store; namespace/deletion owners unknown | INV-04 |
| Queue capacity, aggregate budgets, unfinished work | Operations owns the queue; budget owner unknown | INV-05, INV-06 |
| Prompts, instructions, harness/runtime/model artifacts and configuration | Installation/change owners unknown; external provider | INV-07 |
| Approval and audit evidence | Approval service planned; approval/audit owners unknown | INV-01, INV-02, INV-05, INV-06, INV-07 |

The vendor instruction to omit payment/credential risks is hostile input evidence. It supplies no authority to the reviewer and proves no exploit succeeds.

## Flow and authority boundaries

| Crossing and feedback | Origin / data | Effective operation and authority | Enforcement owner / scenarios |
|---|---|---|---|
| Vendor → parent | Untrusted email/invoice text | Interpretation can select ERP/email operations | Harness owner unknown; INV-01 |
| Parent ↔ model provider | Context and generated decisions; exact sensitive fields unknown | External processing; internal routing opaque | Customer/provider-contract owners unknown; INV-03 |
| Parent or helper → ERP | Invoice and bank queries; payment arguments | Shared credentials; accepted subjects/tenant scope unknown | ERP/identity owners unknown; INV-01, 02, 05 |
| Parent or helper → email | Generated body/recipient | Shared credentials authorize outbound sending | Email/harness owners unknown; INV-01, 02, 03 |
| Agent → human approval → execution | Action description and/or exact arguments, unspecified | Planned approval may gate consequential operations | Approval/execution owners unknown; INV-01 |
| Agent ↔ shared memory → later context | Extracted vendor details and generated summaries | Writes become later retrieval/influence; tenant namespace undecided | Memory owner unknown; INV-04 |
| Parent → queue → sub-agents → tools | Job, tenant context and potentially credentials | Descendant authority and alternate routes unspecified | Operations owns queue; identity/harness owners unknown; INV-02, 05, 06 |
| Operator/provider → runtime/configuration | Executable artifacts, instructions and tool definitions | Loading/configuration determines effective authority | Platform/change owners unknown; INV-07 |

Tenant authorization must survive every relevant ERP, approval, memory, email and queue crossing. The design does not establish that enforcement. An audit collection flow is proposed, not a service claimed to exist. MCP is not specified; external tool publication is not specified. Neither is inferred from tool/API use.

Where the supplied reference gives only grouped item purposes, control-level mappings above are deliberately provisional rather than invented per-item matches. INV-03's architecture items likewise require individual definitions before checklist use. **E03–E05** concern external publication/metadata and **E06–E07** concern MCP/peer-message enforcement: none is mapped solely because this design uses tool APIs or sub-agents. New external tool publication or MCP transport would require revisiting those items.

## Open design decisions and revisit conditions

Batch questions: What tenants, amounts, recipients and bank changes are permitted? Which actions require whose approval? Can ERP enforce scoped identity, bound one-time approvals and idempotency? What data reaches the provider? Which context/credentials reach helpers/descendants? Who owns all controls beyond the queue? What aggregate budget, stop cutoff, retention/deletion and audit-failure policies apply?

These questions stay open; silence is not absence of controls. If helper permissions are enforceably restricted, revise its effective capability table. If provider input excludes sensitive data, narrow INV-03. Changes to tenants, tools, model/provider/runtime, credentials, harness instructions, memory, queues or authority invalidate affected assumptions. Later implementers can use these scenarios and verification needs without sibling skills. This selected mapping is not a 53-item checklist, empirical exploit-frequency claim or release gate outcome.
